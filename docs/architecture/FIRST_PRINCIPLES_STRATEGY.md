# SAP AI 顾问工作台第一性原理推进策略

日期：2026-07-02

## 1. 第一性原理问题

这个产品不是从“AI 聊天”出发，而是从 SAP 顾问每天真正卡住的事情出发：

| 根问题 | 产品必须解决的结果 |
|---|---|
| 每次处理 SAP 问题都要重复解释项目背景、规范和历史结论 | 项目、规范、知识和案件上下文可复用 |
| 直接用通用 AI 容易丢文件、丢证据、丢过程 | 每个案件有真实文件夹和可追溯文件 |
| SAP 资料敏感，不能随便上云 | 本地优先，密钥和客户数据不提交 GitHub |
| AI 结论容易不可追溯 | 结论必须关联案件、文件、SAP 读取记录或知识来源 |
| 知识库容易被 AI 噪声污染 | 候选知识必须人工确认后才能入库 |
| ABAP 和文档规范每个项目不同 | 规范按项目独立复制和演进 |

## 2. 最小不可替代价值

MVP 的最小不可替代价值是：

> 一个 SAP 顾问可以在本地围绕一个案件持续工作，AI 帮他分析和生成交付物，所有过程与结果都自动沉淀到当前案件文件夹，并且后续可以找回。

如果第一阶段没有做到“项目 -> 案件 -> 对话 -> 文件夹 -> 文件树 -> 搜索入口”，后续接入 ADT、飞书或模型都容易变成零散工具拼接。

## 3. 最优路径

| 顺序 | 原因 |
|---|---|
| 先做安全和仓库治理 | 防止后续误提交敏感数据 |
| 再做本地桌面骨架 | 先证明产品主工作区成立 |
| 再做项目、案件、文件 | 这是所有业务能力的承载层 |
| 再做配置中心 | 没有项目和案件，配置没有落点 |
| 再接只读连接器 | 避免一开始陷入 SAP/飞书/API 细节 |
| 再做任务模式 | 任务模式需要文件、规范、连接器共同支撑 |
| 再做规范和知识 | 它们必须服务案件，而不是变成孤立后台 |
| 最后做端到端验收 | 用真实流程证明产品可用 |

## 4. 多 Agent 运行原则

多 Agent 不是越多越好，而是要按边界并行。

| 可并行 | 不可并行 |
|---|---|
| UI 局部页面 | 数据模型未定时改数据库 |
| 只读文档审计 | 多个 Agent 改同一文件 |
| 独立连接器包装 | SAP 写入能力 |
| 独立测试和安全扫描 | 架构和范围决策 |
| 独立产品/UX 审计 | 未冻结的公共接口 |

主控 Agent 必须负责：

1. 冻结阶段目标。
2. 指定每个 Agent 的文件边界。
3. 合并前检查冲突。
4. 对照产品文档做验收。
5. 对每个功能做对抗式审计。

## 5. 阶段目标

| 阶段 | 目标 | 可验收证据 |
|---|---|---|
| Phase 0 | 仓库安全和 GitHub 连接 | `.gitignore`、README、安全文档、Git 远端、敏感扫描 |
| Phase 1A | 本地桌面骨架 | 应用能启动，主界面三栏和底部输入存在 |
| Phase 1B | 最小案件闭环 | 能创建项目、创建案件、保存对话、生成文件、右侧读文件、基础搜索找回 |
| Phase 2 | 配置中心 | 能保存非密钥配置，密钥走安全存储 |
| Phase 3 | 只读连接器 | ADT `status` + `T000` 最小读取、模型最小调用、飞书状态验证 |
| Phase 4 | SAP 案件工作流 | 一个 SAP 问题能形成结论、输出文件、候选知识，但不写 SAP |
| Phase 5 | 规范中心轻量版 | 项目规范独立副本能被 ABAP 开发模式读取 |
| Phase 6 | 知识库和搜索 | 候选知识人工确认，全局搜索可找回 |
| Phase 7 | MVP 验收 | 一条 SAP 顾问工作流端到端跑通 |

## 6. 当前阶段结论

当前最优路径是先完成 Phase 0，然后进入 Phase 1A。

在 Phase 1A 结束前，不应接入真实 SAP、飞书、模型 API，也不应做复杂知识库。

Phase 1B 再补“最小案件闭环”。ADT、模型 API、飞书、规范中心和知识库深度能力仍放到后续阶段，避免主线过早分散。
