# SAP AI 顾问工作台第一性原理推进策略

日期：2026-07-15

> 当前说明：本文前半部分保留最初从 0 到 MVP 的第一性原理推导；原有 Phase 0-8 已成为历史路线。独立 Agent Runtime 已推进到 Phase 56 首个基线，当前事实以 `CONTEXT.md`、源码、Phase 50-56 探针和最新 review 为准。

## 1. 第一性原理问题

这个产品不是从“AI 聊天”出发，而是从 SAP 顾问每天真正卡住的事情出发：

| 根问题 | 产品必须解决的结果 |
|---|---|
| 每次处理 SAP 问题都要重复解释项目背景、规范和历史结论 | 项目、规范、知识和案件上下文可复用 |
| 直接用通用 AI 容易丢文件、丢证据、丢过程 | 每个案件有真实文件夹和可追溯文件 |
| SAP 资料敏感，不能随便上云 | 本地优先，密钥和客户数据不提交 GitHub |
| AI 结论容易不可追溯 | 结论必须关联案件、文件、SAP 读取记录或知识来源 |
| 知识库容易被 AI 噪声污染 | 候选知识必须人工确认后才能入库 |
| ABAP 和文档规范每个项目不同 | 规范按项目独立复制和演进 |
| 依赖外部 AI Harness 会把产品能力绑在另一款工具上 | 自建可替换 Provider、可恢复事件、工具门禁和上下文系统 |

## 2. 最小不可替代价值

MVP 的最小不可替代价值是：

> 一个 SAP 顾问可以在本地围绕一个案件持续工作，AI 帮他分析和生成交付物，所有过程与结果都自动沉淀到当前案件文件夹，并且后续可以找回。

如果第一阶段没有做到“项目 -> 案件 -> 对话 -> 文件夹 -> 文件树 -> 搜索入口”，后续接入 ADT、飞书或模型都容易变成零散工具拼接。

## 3. 最优路径

| 顺序 | 原因 |
|---|---|
| 先做安全和仓库治理 | 防止后续误提交敏感数据 |
| 再做本地桌面骨架 | 先证明产品主工作区成立 |
| 再做项目、案件、文件 | 这是所有业务能力的承载层 |
| 再做配置中心 | 没有项目和案件，配置没有落点 |
| 再接只读连接器 | 避免一开始陷入 SAP/飞书/API 细节 |
| 再做任务模式 | 任务模式需要文件、规范、连接器共同支撑 |
| 再做规范和知识 | 它们必须服务案件，而不是变成孤立后台 |
| 最后做端到端验收 | 用真实流程证明产品可用 |

## 4. 多 Agent 运行原则

多 Agent 不是越多越好，而是要按边界并行。

| 可并行 | 不可并行 |
|---|---|
| UI 局部页面 | 数据模型未定时改数据库 |
| 只读文档审计 | 多个 Agent 改同一文件 |
| 独立连接器包装 | SAP 写入能力 |
| 独立测试和安全扫描 | 架构和范围决策 |
| 独立产品/UX 审计 | 未冻结的公共接口 |

主控 Agent 必须负责：

1. 冻结阶段目标。
2. 指定每个 Agent 的文件边界。
3. 合并前检查冲突。
4. 对照产品文档做验收。
5. 对每个功能做对抗式审计。

## 5. 阶段目标

| 阶段 | 目标 | 可验收证据 |
|---|---|---|
| Phase 0 | 仓库安全和 GitHub 连接 | `.gitignore`、README、安全文档、Git 远端、敏感扫描 |
| Phase 1A | 本地桌面骨架 | 应用能启动，主界面三栏和底部输入存在 |
| Phase 1B | 最小案件闭环 | 能创建项目、创建案件、保存对话、生成文件、右侧读文件、基础搜索找回 |
| Phase 2 | 配置中心 | 能保存非密钥配置，密钥走安全存储 |
| Phase 3 | 只读连接器 | ADT `status` + `T000` 最小读取、模型最小调用、飞书状态验证 |
| Phase 4 | SAP 案件工作流 | 一个 SAP 问题能形成结论、输出文件、候选知识，但不写 SAP |
| Phase 5 | 规范中心轻量版 | 项目规范独立副本能被 ABAP 开发模式读取 |
| Phase 6 | 知识库和搜索 | 候选知识人工确认，全局搜索可找回 |
| Phase 7 | MVP 验收 | 一条 SAP 顾问工作流端到端跑通 |

## 6. 当前阶段结论

Phase 0-8 的基础闭环已经通过后续多个阶段演进为真实桌面应用。当前存在的核心结构性问题不是页面是否有一个“Codex 辅助”按钮，而是消息编排仍主要由业务代码直接调用模型渠道，尚未形成产品自己的 Agent Runtime。

从第一性原理看，下一步必须按以下顺序推进：

1. 先建立可恢复的 Thread / Turn / Item 事件账本，否则流式响应、工具调用、取消和异常恢复都没有可靠事实源。
2. 再统一 Provider Adapter 和运行时事件，否则每种模型协议都会把分支泄露到业务层和 UI。
3. 再加入受控工具循环和权限策略，否则 Skills、MCP 和子 Agent 只会扩大风险。
4. 再做上下文预算、压缩和分层记忆，否则长会话只能依赖无限增长的 Prompt。
5. 最后启用 Skills、MCP 和有限子 Agent；它们是运行时上的能力插件，不是运行时本身。

因此，Codex CLI 只保留为迁移期兼容适配器。核心 Work、Chat、SAP 只读和案件动作必须独立于 Codex 运行。正式设计见 [独立 Agent Runtime 架构](INDEPENDENT_AGENT_RUNTIME.md) 和 [ADR-0002](../adr/0002-independent-agent-runtime.md)。
