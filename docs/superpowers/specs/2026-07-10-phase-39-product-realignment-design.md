# Phase 39 产品重整与多模型渠道设计

日期：2026-07-10

## 1. 结论

当前项目已经具备本地桌面壳、Project / Case 文件闭环、SAP 只读连接、模型连接器、飞书 CLI、规范中心和知识审核等重要基础，但用户界面仍像连续叠加功能后的开发样机。最主要的问题不是配色，而是界面承诺、数据归属和实际行为没有完全一致。

本轮重构不推翻安全可靠的底层能力，先重整用户每天都会经过的主路径：

1. 默认进入 Work，而不是能力尚不完整的 Daily Chat。
2. Project 负责隔离客户与配置，工作文件夹（底层 Case）负责承载正式任务和成果。
3. 中间区域只突出连续对话，案件动作和 SAP 只读取证按需展开。
4. 右侧始终服务当前工作文件夹，不变成常驻 Dashboard。
5. 一个 Project 可以配置多个模型渠道；每个渠道测试后保存完整模型列表。
6. 对话窗口可以按渠道选择该渠道已获取的任意模型；测试模型只是健康检查记录，不是唯一白名单。
7. SAP 写入、外部发布、密钥展示和任意文件访问仍保持硬限制。

## 2. 用户真正要完成的工作

目标用户是个人 SAP 顾问，不是系统管理员，也不是开发本产品的程序员。用户每天的核心任务只有四类：

| 用户目标 | 系统应提供的最短路径 |
|---|---|
| 处理正式问题 | 选择 Project -> 打开工作文件夹 -> 连续对话 -> 生成和查看成果 |
| 临时问答 | 进入 Chat -> 选择可用模型 -> 对话，不关联 Project / Case 文件 |
| 补充真实依据 | 在当前案件按需读取 SAP 只读证据、项目规范和已审核知识 |
| 管理基础能力 | 在项目配置中添加渠道、保存密钥、测试连接并获取模型 |

所有页面和按钮都必须直接服务其中一个目标。没有实际行为、只展示阶段状态、或与主路径重复的控件不应常驻。

## 3. 现状审计

### 3.1 应保留的基础

- Electron main process 持有本机权限，renderer 通过窄 IPC 调用。
- 密钥使用系统安全存储，项目文件和 renderer 状态不保存明文。
- SAP 连接和对象证据默认只读，没有 SAP 写入接口。
- Project -> Case -> 本地文件的成果闭环已经存在。
- 候选知识必须人工审核后才能发布为正式知识。
- 模型连接器已经支持 OpenAI compatible `/models` 和最小 chat 测试。
- 配置数据结构已经允许一个 Project 保存最多 6 个模型渠道。

### 3.2 必须纠正的冲突

| 级别 | 冲突 | 用户影响 | 本轮处理 |
|---|---|---|---|
| P0 | 页面最小宽度与三栏固定宽度相加超过窗口 | Windows 缩放时右侧被裁切 | 是 |
| P0 | 配置页只编辑 `apiProviders[0]` | 多渠道能力实际不可用 | 是 |
| P0 | 对话只允许使用 `lastVerifiedModelId` | 获取到的其他模型无法选择 | 是 |
| P0 | 普通案件对话无视当前权限选择，固定发送 `request_approval` | 界面与实际权限不一致 | 是 |
| P1 | Chat 是默认首页，但 Work 才是产品核心 | 用户第一眼看不到主工作流 | 是 |
| P1 | 顶栏、附件、语音等按钮没有实际行为 | 降低产品可信度 | 是 |
| P1 | 新建 Project / 工作文件夹表单长期占据左栏 | 导航区域拥挤、难扫描 | 是 |
| P1 | SAP 取证表单长期占据主输入区 | 连续对话被技术表单打断 | 是 |
| P1 | 每条 AI 回复重复安全说明 | 重要内容被模板噪声淹没 | 是 |
| P1 | 案件动作名称与部分实际产物不完全一致 | 用户无法预测按钮结果 | 是 |
| P1 | 搜索结果不能直接打开目标 | 历史追溯链路未闭环 | 是 |
| P1 | 窄窗口直接隐藏知识审核详情 | 人工入库流程可能不可达 | 是 |
| P2 | `App.tsx` 与 `ConfigCenter.tsx` 过大 | 修改容易互相影响 | 分阶段拆分 |
| P2 | 新建 Project 自动带一个内部初始 Case | 归属关系不够透明 | 兼容迁移阶段处理 |

## 4. 第一性原理

### 4.1 一个屏幕只回答三个问题

主工作台必须让用户一眼确认：

1. 我现在在哪个 Project / 工作文件夹？
2. 我正在和谁对话、会使用哪个渠道和模型？
3. 这次工作产生了哪些本地文件？

不直接回答这三个问题的配置和诊断信息应按需展开或进入专门页面。

### 4.2 基础设施与业务上下文分开

- 模型渠道是调用基础设施；模型是渠道返回的可选能力。
- Project 决定当前工作允许使用哪些渠道，并隔离密钥和配置。
- Case 决定业务上下文、对话、证据和成果文件。
- 选择模型不应改变 Project / Case 的数据归属。
- Daily Chat 不读取 Project / Case 内容。后续可复用已授权渠道，但不得把聊天内容写入 Project。

### 4.3 测试记录不是使用白名单

渠道测试分成两步：

1. 拉取模型列表，证明地址、密钥和模型接口可用。
2. 选取一个模型执行最小对话，证明 chat 接口可用。

`lastVerifiedModelId` 只记录第二步使用的探针模型。只要渠道配置未变化、模型仍在本次获取列表中，该渠道的其他模型也可以在对话窗口选择。实际调用失败时应返回可理解错误，并允许切换模型。

### 4.4 安全能力不得因重构变弱

- 密钥仍不进入 renderer 持久状态、日志、Markdown、截图或模型上下文。
- renderer 不直接请求模型、SAP 或飞书。
- SAP 仍只允许明确列出的只读读取。
- 不新增删除、SAP 写入、自动发布或生产变更能力。
- 模型只接收已经过安全裁剪的 Case 上下文。

## 5. 目标信息架构

```text
应用
├─ Work（默认）
│  ├─ 左侧：搜索、Project、工作文件夹、新建入口
│  ├─ 中间：当前工作文件夹对话
│  │  ├─ 紧凑上下文状态
│  │  ├─ 消息流
│  │  └─ 输入、模型选择、案件动作、权限、按需 SAP 取证
│  └─ 右侧：文件 / 项目配置摘要
├─ Chat
│  ├─ 左侧：新对话、历史对话
│  └─ 中间：纯对话，不显示案件动作和文件面板
├─ 配置中心
│  ├─ SAP 只读连接
│  ├─ AI 渠道列表与当前渠道编辑
│  └─ 可选能力：飞书、Codex、本地存储
├─ 规范中心
└─ 知识库
```

## 6. 多渠道模型交互

### 6.1 配置中心

- 左侧或卡片顶部展示渠道列表，显示名称、启用状态、验证状态和模型数量。
- `添加渠道` 创建新的 OpenAI compatible 草稿，最多 6 个。
- 切换渠道后编辑该渠道的名称、Base URL、类型、API Key 和启用状态。
- API Key 输入按渠道独立保留，避免切换时丢失尚未保存的内容。
- 保存只更新当前 Project 的普通配置和该渠道密钥。
- `测试并获取模型` 使用已保存配置，返回模型数、测试模型、时间和明确错误。
- 本轮不提供删除渠道，避免遗留密钥无法清理；后续必须设计安全删除与密钥清理确认。

### 6.2 对话窗口

- 模型选择器只显示启用、真实 HTTP 验证通过且模型列表非空的渠道。
- 渠道内显示本次获取到的全部模型，并支持名称、渠道和能力搜索。
- 当前选择同时显示渠道名与模型名。
- 没有合格渠道时明确使用本地草稿，不伪装成真实 AI 回复。
- 模型选择只存在一个位置，避免顶部、底部和设置页各自维护不同选择。

## 7. 视觉与布局规则

本产品采用安静、实用、适合长时间工作的桌面工具风格：

- 顶栏只保留产品名、本地模式和当前上下文，不模拟操作系统窗口按钮。
- 左栏基准宽度 248-264px；右栏基准宽度 300-328px；中间允许收缩到 0。
- 不设置阻止窗口缩放的 `body min-width`。
- 低于三栏舒适宽度时，右栏自动收起，可由用户重新打开。
- Project 列表使用树状/行式导航，不堆叠大卡片。
- 新建表单只在用户点击后出现。
- 消息正文优先，安全边界使用一个紧凑状态条表达，不在每条消息重复。
- 案件动作使用紧凑选择器和单一生成按钮，确认面板只在用户发起动作后出现。
- 所有可见按钮必须能执行实际动作；未开发功能不占用主界面。

## 8. 分阶段重构

### Phase 39：可信主路径与多渠道模型

- 修复三栏溢出和桌面菜单噪声。
- Work 作为默认入口。
- 移除无效顶栏、附件和语音控件。
- 新建表单与 SAP 只读取证按需展开。
- 配置中心支持多渠道添加、切换、保存和验证。
- 对话可选择已获取的全部模型。
- 普通对话使用当前权限模式。
- 搜索结果可直接打开 Project、工作文件夹、知识或文件。
- 隐藏 Project 提供恢复入口，知识审核详情在窄窗口使用覆盖层显示。
- 窗口启动尺寸自动适配当前显示器可用工作区和 Windows DPI 缩放。
- 案件动作名称、确认面板保存位置和实际生成文件一一对应。

### Phase 40：行为语义闭环

- 权限改为 Project 默认、Case 覆盖，并持久化。
- 移除自动初始 Case 或将其迁移为用户可理解的收件箱。
- 为模型渠道提供带密钥清理确认的安全删除能力。

### Phase 41：Daily Chat 与模型基础设施解耦

- 建立个人级模型渠道注册表。
- Project 只保存允许使用和默认选择，不复制基础设施配置。
- 当前 Daily Chat 已可临时复用当前 Project 授权的渠道模型，消息仍不写入 Project / Case；本阶段再迁移为个人级渠道选择，消除对当前 Project 的依赖。
- 提供现有项目级渠道的可回滚迁移。

### Phase 42：中心页面与响应式完善

- 继续清理规范和知识页面残留的开发期说明与不可用按钮。
- 键盘导航、焦点、错误提示和长文本适配。

### Phase 43：模块拆分与回归测试

- 从 `App.tsx` 拆出 Shell、Sidebar、Conversation、Composer、ContextPanel。
- 从 `ConfigCenter.tsx` 拆出 SAP、ModelChannels、Feishu、Codex 配置模块。
- 增加关键用户流程的 Playwright/Electron UI 回归。
- 完成安全、产品语义和视觉三类对抗式审查。

## 9. Phase 39 验收标准

1. 1440x920、1280x800 和 Windows 缩放场景不出现横向裁切。
2. 启动后默认显示 Work 和当前工作文件夹。
3. 顶栏和输入区没有无效按钮。
4. 新建 Project、工作文件夹和 SAP 取证表单默认不占空间。
5. 一个 Project 可添加并保存至少两个模型渠道。
6. 每个渠道可独立保存 API Key、测试并保存模型列表。
7. 对话模型选择器按渠道展示全部已获取模型。
8. 选择非探针模型时 main process 接受请求，仍经过安全上下文裁剪。
9. 普通对话发送当前选择的权限模式。
10. `npm run check`、`npm run build`、Phase 27-39 probes、安全预检和 `git diff --check` 全部通过。
