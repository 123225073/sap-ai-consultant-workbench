01 / 先把边界说清

Codex 不是“一个模型”，而是一台受控的工作编排机。

模型负责理解与决策；App / CLI 负责把决策变成可见、可控、可追溯的工作。没有后者，模型只能“建议”；有了后者，才会出现会话、文件、工具、审批、恢复、记忆这些你在 Codex 中感受到的能力。

最重要的一句话
Agent = 模型 + 上下文 + 工具 + 控制循环 + 安全边界 + 状态。

它的难点通常不在“再换一个更强模型”，而在于如何让每一步都正确地拿到信息、只做被允许的动作、在中断后还能继续、并把结果变成可以复查的证据。

03 / 发动机

Agent Loop：不是“一问一答”，而是一个带刹车的循环。

普通聊天通常到模型输出文字就结束。Agent 则把工具结果重新喂给模型，让它继续观察、修正、执行或交付。循环的结束不是“模型没话说”，而是满足完成条件、被用户中断、达到预算/权限边界，或需要人来做决定。

可点击每一站 / 或自动播放

这个演示故意把“思考”隐藏，只展示外部可观察、可审计的工作状态。优秀的 Agent 产品不必暴露内部推理，也依然能让用户知道它在做什么、为什么暂停。

01 · 接收任务
先创建或恢复一个工作线程。把用户原话保留为不可替换的意图来源；不要过早把它“总结坏了”。
event: thread/start → turn/start
state: active · waiting for input context

官方 app-server 公开了 Thread（会话）→ Turn（一次交互）→ Item（消息、命令、编辑等最小记录）的模型，并会在回合中流式推送 item 事件。这正是“可恢复的 Agent”常见的骨架。

04 / 你听说的“路由”到底是什么

路由不是一个神秘模型；它是“把对的东西送到对的地方”的一组规则。

初学者常把 Router 想成一个固定的“意图分类器”。真实产品里它至少有四种含义，很多时候由显式规则、元数据、模型判断和用户确认共同完成。

ROUTE / 01

任务路由

这是“普通问答、代码修改、深度研究、执行工作流”中的哪一种？决定给模型什么开发指令、可用工具和完成标准。MVP 不要急着训练分类器：让用户选模式 + 用关键词规则已足够。

ROUTE / 02

上下文路由

从项目规则、当前 Case、文件、检索结果、会话摘要中，挑哪些放进本回合。它本质上是“相关性 + 权限 + token 预算”的选择问题。

ROUTE / 03

工具路由

工具很多时，不能把全部说明都塞给模型。按当前任务和权限加载文件工具、浏览器、MCP 工具或某个 Skill 相关能力；必要时延迟加载。

ROUTE / 04

权限路由

同样的“写文件”请求，在只读、工作区可写、完全访问三种环境里结果不同。对高风险路径，路由的结果应当是“请求人类确认”，不是悄悄绕过。

不要混淆：Router ≠ Loop

Router 决定“走哪条路”；Loop 决定“走完后是否继续”。

ROUTER
选择能力
上下文包工具集合审批策略模型/预算
好的路由可解释：界面应该让人看出当前用了什么资料、什么能力、为什么需要审批。
05 / 核心零件辨析

Skills、MCP、Plugin、Hook：不要把四件不同的东西揉成一团。

它们都能让 Agent “更会做事”，但作用点完全不同。理解这个差别，是你设计产品结构的分水岭。

S

Skill

会做事的方法册

一份可复用的工作说明：何时使用、先读什么、怎样产出、如何验证。它主要改变模型的行为与流程，不天然获得任何系统权限。

类比：给新同事的 SOP。
最小形态：一个 SKILL.md。
M

MCP

连外部能力的通用插座

Model Context Protocol 是客户端与外部工具/资源服务之间的协议。一个 MCP Server 可以提供工具、资源、提示或认证流程；它不等于某一个具体工具。

类比：统一规格的 USB-C。
最小形态：一个暴露工具清单的本地/远程服务。
P

Plugin

可安装的能力包

插件是产品层的“包装盒”。它可以打包多个 Skill、App/Connector、模板和配置，让某类工作一键可用。插件本身仍应继承底层 App 的权限。

类比：摄影套装，不是镜头本身。
最小形态：清单 + 指令 + 依赖能力。
H

Hook

事件发生时的守门员

Hook 在特定生命周期事件前后触发，例如工具调用前检查、回合结束时通知。它更适合做策略、审计和自动化护栏，而非让模型自由决定。

类比：门禁与流水线传感器。
最小形态：事件匹配 + 受信任脚本。
快速判断
它主要解决什么？
它应不应该直接拥有高权限？
Skill
让模型按正确流程工作
不应；Skill 是说明，不是授权
MCP
连接外部工具、数据与资源
由 Server 与宿主策略共同限制
Plugin
分发一整套工作能力
不应绕过其中每个 App/工具的权限
Hook
在关键事件施加规则或自动动作
尤其需要信任、签名/哈希与超时控制
06 / 记忆不是一个数据库字段

“跨 Session 记忆”真正要解决的，是取回正确过去，而不是把一切都塞回模型。

模型没有永久大脑。每次请求都只看见这次传入的上下文。所谓记忆，是宿主系统把过去的信息保存、提炼、检索、筛选后，再以可控方式放回模型输入的过程。

L0本回合上下文本次请求实际送进模型的文字、工具、附件短 / 易满
L1会话记录Thread / Turn / Item：可恢复、可分页的原始历史可追溯
L2工作记忆目标、计划、当前文件、待办、最新观察本任务
L3项目记忆AGENTS.md、规范、偏好、项目知识、索引有边界
L4长期记忆从多个会话提炼并整合的稳定事实与经验跨 Session
L0 / 本回合上下文

模型眼前真正看见的桌面。

系统提示、用户消息、选中的文件片段、工具定义、临时摘要共同组成。它不是“数据库”，而是一包有 token 上限的输入。

设计动作：严格预算；只放与当前目标相关、且允许模型看到的内容。
一个常见误解：“向量数据库 = 记忆”不对。向量检索只是 召回候选信息 的一种方式；真正可靠的记忆系统还需要来源、权限范围、版本、时效、冲突处理、摘要更新与是否注入上下文的决策。

一次“跨 Session 接上工作”的正确路径

SESSION A原始过程对话、工具调用、文件修改、验证结果
→
AFTER IDLE提炼把有价值的事实、决定、偏好写成结构化记忆/摘要
→
SESSION B检索候选按项目、权限、任务与时间筛选，而非全量读取
→
NEW TURN注入小包来源可见的少量相关上下文，再继续 Loop

公开 Codex 核心代码已出现 memory pipeline：对符合条件、已闲置的会话提取结构化 memory，再进行全局整合；其设计也明确包含并发上限、任务租约、失败退避、秘密脱敏与本地记忆目录。具体功能仍可能随版本变化，因此把它视为“公开的实现方向”，而不是所有桌面版本都保证开启的承诺。

07 / 为什么桌面 App 不是一堆 API 调用

界面、Agent 引擎和系统能力之间，需要一条“事件总线”。

Codex 的公开 app-server 采用双向 JSON-RPC，支持 stdio、WebSocket 等传输；客户端启动线程与回合后，持续接收消息增量、工具进度和完成事件。你做自己的产品时不必照抄 Rust，但一定要继承这种“命令 + 流式事件 + 可持久化状态”的思路。

最小事件模型

  1. 命令：UI 说“开始这一回合”。
  2. 事件：引擎连续报告“消息增量、工具已开始、输出到达、工具已完成”。
  3. 状态：每个 Thread、Turn、Item 被持久化；崩溃后可读回。
  4. 控制：UI 可以中断、继续、分叉、归档，而不是只能等回答。
官方公开接口中：Thread 是用户与 Agent 的会话；Turn 是一次用户交互；Item 是该回合中的消息、命令、文件编辑等最小可持久化条目。这个概念模型非常适合直接借鉴。
08 / 最容易被低估的部分

安全不是最后加一个“确认按钮”，而是每层都有边界。

模型会误判，工具会失败，文本也会包含提示注入。一个能上线的 Agent 产品，必须把“模型建议了什么”和“系统实际做了什么”明确分开。

四道护栏：任何一道都不能只靠模型自觉

先只读，后写入；先范围小，后扩展
1

能力最小化

工具按用途与范围设计，不给“任意 shell + 任意路径 + 任意网络”这种万能钥匙。文件工具应限定工作区，业务系统先做只读。

CAPABILITY ALLOWLIST
2

执行前审批

把读取、写入、外部发送、删除、付款等动作分级。审批展示“会影响什么”，而不只问“要不要继续”。可审批的是具体动作，不是抽象信任。

RISK-BASED APPROVAL
3

隔离与净化

工具进程运行在沙箱/受限权限下；密钥留在主进程或系统凭据库；工具输出进入模型前要限长、去秘密、带来源，防止脏数据反向控制 Agent。

SANDBOX + SECRET BOUNDARY
4

可追溯与可撤销

保存谁触发、做了什么、用什么输入、输出在哪里、验证是否通过。优先设计草稿、预览、diff、回滚；Hook 与第三方能力要有信任状态和超时。

AUDIT + RECOVERY
09 / 复刻一台自己的 Agent 工作台

从零到一 SOP：先做一条可靠的窄闭环，再增加“聪明”。

不要一开始同时做多 Agent、长期记忆、十个 MCP、自动部署。最强的学习路径是：让一个 Agent 在一个受限文件夹中，能完成一类任务并拿出验证结果。

你真正要交付的，不是聊天框。

每一阶段都应留下一个可演示的“纵切面”：用户输入一个真实任务，系统完成有限动作，界面实时显示过程，并留下可验证产物。

建议技术路线：
Desktop: Electron + React + TypeScript
Runtime: Node / Rust 任一
State: SQLite + 本地文件
Model: 先接一种 API
Tools: 先只读文件 + 受控写文件
PHASE 01

定义一个窄任务与完成标准

例如“在指定项目文件夹中分析报错并生成 Markdown 报告”。明确输入、允许动作、产物、验证命令与不做什么。

一页任务契约
PHASE 02

先搭 Thread / Turn / Item 状态机

新建、恢复、取消、完成、失败都要有状态；消息、工具、产物都作为 Item 记录。先存 SQLite/JSONL 都可以。

可恢复会话
PHASE 03

完成最小 Agent Loop

把模型返回的 tool call 交给宿主执行，再把工具结果送回下一轮。加入最大回合数、超时、取消、错误收敛。

一次工具闭环
PHASE 04

做一个小而严的工具注册表

每个工具有名称、描述、参数 schema、风险级别、执行器、超时、输出清洗规则。先做读文件、搜文件、写草稿、跑测试。

Tool Registry
PHASE 05

把权限与审批放到模型外

按 read / write / destructive / external 分级；执行器二次校验路径与参数；密钥与 UI、模型上下文隔离。

Policy Gate
PHASE 06

接入项目指令与 Skill

加载项目范围的规则文件，发现可用 Skill；用户点选或显式触发 Skill 后，把相关指令注入当前回合。不要让 Skill 自己变成权限后门。

受控 SOP
PHASE 07

再接 MCP，但从只读服务开始

把 MCP 当成外部工具来源，先列能力、查看认证状态、调用只读工具、记录来源与参数。远程 MCP 与插件需单独审查。

一条安全连接
PHASE 08

做摘要、检索与长期记忆

先解决上下文超长：压缩旧历史并保留原文。再做带来源的检索。最后才让后台任务提炼跨会话记忆，并允许用户查看/删除。

可控跨会话
PHASE 09

把验证与评估产品化

对每类任务准备样本、预期产物、工具调用边界与回归测试。记录成功率、人工接管、工具失败、审批拒绝与 token 成本。

真实可迭代
// 够用的最小 Loop；所有副作用都穿过 policy 与 executor
while (turn.isActive && steps < MAX_STEPS) {
  context = buildContext(thread, projectRules, selectedSkills, retrievedFacts, toolCatalog);
  modelEvent = await model.stream(context);
  if (modelEvent.type === 'final') break;
  if (modelEvent.type === 'tool_call') {
    decision = await policy.check(modelEvent, user, workspace);
    if (decision.needsApproval) await askUser(decision);
    result = await executor.run(modelEvent, decision); // 沙箱、超时、审计、净化
    thread.append(result);
  }
  steps++;
}
// 结束后：验证 → 保存产物 → 生成摘要/候选记忆 → 呈现最终答复
10 / 少走弯路

三个最常见、也最伤产品的误区。

“给模型一个万能工具就行。”

结果是无法预测的权限边界、无法解释的副作用和极高的注入风险。模型对文字的理解能力，不等于它应拥有操作系统的全部能力。

FIX → 工具细分 + 参数 schema + 路径/域名 allowlist + 审批。

“记忆越多，Agent 越聪明。”

全量历史会挤占上下文、放大旧错误、混入敏感信息，还会让模型忽略眼前任务。长期记忆最重要的是“忘记、筛选、溯源”。

FIX → 原文归档、摘要压缩、检索召回、用户可见的注入来源。

“多 Agent 就是并行调用多个模型。”

没有明确拆分、独立上下文、输出契约与汇总者，多 Agent 只会重复花钱、互相污染、增加调试复杂度。单 Agent 闭环稳定前不要上。

FIX → 先一个主线程；确有独立子问题时才派生子任务并汇总证据。
